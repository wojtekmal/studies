# Architektura sio2project

---

# Co robi system sprawdzający?

1. Uczestnik wysyła rozwiązanie
2. System **kompiluje** kod
3. Uruchamia go na **testach** w bezpiecznym środowisku (sandbox)
4. Porównuje wyniki, mierzy **czas i pamięć**
5. Wylicza **punkty** i pokazuje wynik (zależnie od zasad konkursu)

Trudności: bezpieczeństwo, powtarzalność pomiarów, skala (setki uczestników naraz).

---

# Komponenty

- **OIOIOI** – aplikacja webowa (Django): konkursy, zadania, zgłoszenia, rankingi
- **PostgreSQL** – baza danych
- **Celery + broker (RabbitMQ)** – asynchroniczne przetwarzanie zgłoszeń (evalmgr)
- **filetracker** – przechowywanie plików: testy, kody źródłowe, wyniki
- **sioworkersd** – dyspozytor zadań oceniania
- **sioworkers** – maszyny, które kompilują i uruchamiają rozwiązania
- **sio2jail** – sandbox z dokładnym pomiarem czasu (liczba instrukcji)

---

# Jak to się łączy

```text
  Przeglądarka
       │

  ┌──────────┐      ┌────────────┐
  │  OIOIOI  │◄────►│ PostgreSQL │

  └────┬─────┘

  │ sioworkersd │────────────►│  sioworkers │──► sio2jail

                                     │
  ┌─────────────┐   pliki            │
  │ filetracker │◄───────────────────┘
  └─────────────┘   (OIOIOI też z niego korzysta)
```

---

# Droga zgłoszenia (w skrócie)

1. Formularz w OIOIOI → zapis zgłoszenia w bazie, kod w filetrackerze
2. **evalmgr** buduje środowisko oceniania (lista kroków zależna od typu konkursu)
3. Kroki wymagające uruchomienia kodu trafiają do **sioworkersd**
4. **sioworker** pobiera pliki z filetrackera, kompiluje, uruchamia w sio2jail
5. Wyniki wracają do OIOIOI → punktacja → raport dla uczestnika

Szczegóły na osobnych zajęciach („ocenianie zgłoszeń od początku do końca”).

# OIOIOI od środka – pierwsze spojrzenie

- Duży projekt Django: dziesiątki aplikacji w katalogu `oioioi/`

# Docker w pigułce

---

# Po co Docker?

- Cały system (web, baza, broker, filetracker, workery) uruchamiany **jedną komendą**
- To samo środowisko u wszystkich – mniej „u mnie działa”
- Nie instalujemy PostgreSQL ani RabbitMQ bezpośrednio na swoim systemie

---

# Podstawowe pojęcia

- **Obraz** – szablon systemu plików + konfiguracja (budowany z `Dockerfile`)
- **Kontener** – uruchomiona instancja obrazu
- **Wolumen** – trwałe dane poza kontenerem
- **docker compose** – opis wielu kontenerów i ich połączeń w pliku YAML

---

# `easy_toolbox.py` – codzienne narzędzie

Nakładka na `docker compose -f docker-compose-dev.yml`:

```bash
./easy_toolbox.py build     # zbuduj obrazy
./easy_toolbox.py up        # uruchom wszystkie kontenery w tle
./easy_toolbox.py run       # serwer Django + webpack
./easy_toolbox.py bash      # wejdź do kontenera web
./easy_toolbox.py stop      # zatrzymaj kontenery
./easy_toolbox.py down      # zatrzymaj i usuń kontenery
./easy_toolbox.py --help    # pełna lista komend
```

Uwaga: `./easy_toolbox.py wipe` **usuwa wszystkie dane** (wolumeny).

Pełne zajęcia o Dockerze będą później.

# Warsztat: instalacja OIOIOI

---

# Krok 0: przygotowanie

- Zainstalowany Docker (Linux: Docker Engine, macOS/Windows: Docker Desktop lub alternatywa)
- Na Linuksie: dodaj użytkownika do grupy `docker` (grupa jest tworzona przy instalacji, ale użytkownik nie jest do niej dodawany automatycznie)

```bash
sudo usermod -aG docker $USER        # potem wyloguj się i zaloguj ponownie
sudo systemctl enable --now docker   # jeśli usługa nie działa (np. Fedora, Arch)
```

- Uwaga: członkostwo w grupie `docker` = w praktyce uprawnienia roota

- Sklonuj repozytorium (najlepiej swój fork):

```bash
git clone https://github.com/<login>/oioioi.git
cd oioioi
```

---

# Krok 1: budowanie i uruchomienie

```bash
./easy_toolbox.py build
./easy_toolbox.py up
./easy_toolbox.py run
```

- `build` za pierwszym razem trwa kilka–kilkanaście minut
- po pierwszym uruchomieniu `up` należy poczekać kilka minut na zaaplikowanie migracji
- `run` działa na pierwszym planie – zostaw go w osobnym terminalu

---

# Krok 2: pierwsze logowanie

- Otwórz http://localhost:8000
- Login: `admin`, hasło: `admin`
- Opcjonalnie przykładowy konkurs z zadaniem:

```bash
./easy_toolbox.py populate-sample-data
```

---

# Krok 3: pełny cykl zgłoszenia

1. Utwórz konkurs (panel administratora)
2. Dodaj zadanie z paczki, np. przykładowa paczka `sum.zip`:
   https://github.com/sio2project/oioioi/blob/master/oioioi_cypress/cypress/fixtures/sum.zip
3. Wyślij rozwiązanie – poprawne i błędne
4. Sprawdź wynik i raport z testów
5. Zajrzyj do logów: `docker compose -f docker-compose-dev.yml logs -f`

---

# Typowe problemy

- **Brak uprawnień do Dockera** → grupa `docker`, ponowne zalogowanie
- **Port 8000 zajęty** → zatrzymaj inny serwer lub zmień port
- **Apple Silicon / Windows** → wolniejsze budowanie, możliwe problemy z sio2jail; zgłaszajcie od razu
- **Zgłoszenie „wisi”** → sprawdź logi workerów i Celery
